GITHUB WORKFLOW

LOCAL: create and commit a migration after changing prisma/schema.prisma

docker compose -f docker-compose.dev.yml up -d --build
docker compose -f docker-compose.dev.yml exec dashboard-dev npx prisma migrate dev --name describe_the_change
docker compose -f docker-compose.dev.yml exec dashboard-dev npx prisma generate

git status
git add prisma/schema.prisma prisma/migrations package.json package-lock.json Dockerfile.prod docker-compose.prod.yml src
git commit -m "Describe the change"
git push origin main


NAS PRODUCTION: deploy code and apply a new migration

1. SSH into the NAS and move to the cloned repository:

	ssh <nas-user>@<nas-host>
	cd /volume1/docker/dashboard

2. Pull the release from GitHub:

	git fetch origin
	git checkout main
	git pull --ff-only origin main

3. Confirm the production `.env` remains on the NAS and contains the NAS values,
	especially `NEXTAUTH_URL` and `DATABASE_URL`. Do not commit `.env` to GitHub.
4. Confirm the production network exists:

	sudo docker network inspect web-network

5. Rebuild and recreate the application stack:

	sudo docker compose -f docker-compose.prod.yml up -d --build

6. The dashboard container automatically runs this before starting Next.js:

	npx prisma migrate deploy

7. Verify the migration and application logs:

	sudo docker compose -f docker-compose.prod.yml logs --tail=100 dashboard
	sudo docker compose -f docker-compose.prod.yml ps

8. Open the production site and verify the changed feature.

To install the repository on the NAS for the first time:

	cd /volume1/docker
	git clone <github-repository-url> dashboard
	cd dashboard
	sudo docker network inspect web-network
	sudo docker compose -f docker-compose.prod.yml up -d --build

IMPORTANT:

- Do not run `docker compose down -v` in production. It can delete the PostgreSQL volume and database data.
- Do not run `prisma migrate dev` against production. Use `prisma migrate deploy`.
- Do not run the demo seed in production. The production Compose file intentionally runs migrations only.
- If the migration fails, do not delete the database container or volume. Read the logs, fix the migration, and rerun the deployment.


NAS: BACK UP THE WHOLE DATABASE (Japanese, finance, calendar, todos, users, everything)

From /volume1/docker/dashboard:

sudo sh scripts/backup-database.sh /volume1/backups/dashboard

Creates a new dated .dump file each run. The app stays running.
Uploaded documents are separate files; use the combined backup procedure in
README.md / docs/FINANCE_MAINTENANCE.md to include them as well.
